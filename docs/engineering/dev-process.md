# pidesk 开发流程(v1.0)

> 2026-09-10 定稿。裁决来源:与用户逐条确认的 P1~P4(见文末裁决记录)。
> 层级:product-plan.md(做什么)> 本文档(怎么流转)> AGENTS.md(日常纪律)。冲突时修订下游文档并向对齐。

---

## 1. 阶段模型

```
S 规划 ✅ → E 详设(当前) → M 里程碑编码 → A 里程碑验收 → R 发布/复盘 → 下一里程碑
```

- **E 详设**:产出 `engineering/pi-protocol.md`、`engineering/m1-design.md`、`engineering/m1-tasks.md`,经用户确认(§8 环节一)后 M1 方可开工。
- **M→A→R**:每个里程碑循环一次;出口标准以 product-plan §11 为准。

## 2. 角色分工

| 角色 | 职责 | 边界 |
|------|------|------|
| 用户 | 方向裁决、三环节确认(§8)、里程碑终验 | 不参与日常执行循环 |
| 主线程(编排 pi) | 任务拆解、派发、验收、集成、git 提交推送 | 不直接写实现代码 |
| 子线程(执行 pi) | 执行单一任务卡,自验闭环 | 隔离于 `/root/.pi-worker/`;禁止 git commit/push;禁止自行新增依赖 |

派发一律经 `scripts/dispatch.sh`(纪律/环境约束/自验标准机械化注入),默认模型 `qwen3.8:q3xl-16k`,任务卡按 16k 上下文预算拆分,超预算拆卡不换大上下文。

## 3. 任务卡生命周期

```
draft → ready(过DoR) → dispatched → self-verified(子线程自验绿)
                                          ↺ rework(带问题清单,≤3轮)
       → accepted(主线程验收过) → merged(合入 main,一卡一 commit)
任意环节 >3 轮失败 → 熔断升级用户(§8 环节三)
```

- **DoR(派发就绪)**:目标 / 涉及文件路径 / 约束引用 / 验收命令(`-v`)/ 依赖任务已 merged / 16k 预算内。
- **DoD(完成定义)**:编译过 → 静态门槛过 → 验收命令绿 → **主线程读 diff 对照规格**(不得只跑测试)→ 无越范围改动 → 涉及新依赖已按 §7 报备。
- **提交纪律**:Conventional Commits 中文描述;一卡一 commit(revert 单元);main 直合,**不搞 PR 流**(P1);推后 CI 兜底,红则最高优先修复。

## 4. 测试策略(分层)

| 层 | 内容 | 工具 | 时机 |
|----|------|------|------|
| L1 单元 | 分帧器/协议解析/会话状态机等纯逻辑 | vitest | M1 起;协议关键模块行覆盖 ≥80%(红线) |
| L2 集成 | 对真 pi binary 的 RPC 会话(隔离 env) | vitest + spawn | M1 起 |
| L3 E2E | Electron 窗口级全链路 | Playwright `_electron` | **M2 进 CI**(P2);mock pi 后端为主(快、稳),每里程碑加 1 条真模型冒烟仅在出口跑;M1 仅手动清单 + 可选本地 mock 冒烟 |
| L4 专项 | 双向隔离验收清单;pi 升级四项冒烟(`scripts/regression-pi.sh`) | 脚本 | M1 出口必过;pi 换版本必过 |

E2E 纪律(进 CI 后生效):界面元素挂 `data-testid` 契约;只断言稳定终态,不断言流式中间帧;禁止 sleep 式等待。

## 5. 版本与发布

- semver `0.x`;`0.1.0` = M1 交付;里程碑出口打 tag(`m1`、`m2`…)+ `CHANGELOG.md` 按里程碑分节。
- 里程碑出口 = 用户终验通过(§8 环节二),包含 **Windows 真机实测**。

## 6. CI/CD(GitHub Actions)

- **push 触发**:install → lint → typecheck → L1+L2 测试 → build。
- **产物矩阵(P3)**:M1 优先保证 **Windows 产物**(windows runner 出安装包);Linux 由 WSL 开发机本地覆盖;**macOS 延后 M5**(与 unsigned 议题合并处理)。
- **E2E 进 CI 时点 = M2**(P2);CI 中 L2 需 pi binary,用对应平台 standalone + 缓存。

## 7. 依赖管理(报备制,P4)

- 原则:**仅在必须时引入**;**无需用户批准,但必须告知**。
- 程序:主线程评估必要性 → 登记本仓库 `docs/DEPENDENCIES.md`(包/版本/用途/License/日期)→ 在相关验收汇报中向用户列明。
- 子线程禁止自行引入依赖;派发卡中写明允许使用的依赖范围。

## 8. 必经用户确认的环节(三环节)

| # | 环节 | 时点 | 用户动作 | 回答的问题 |
|---|------|------|---------|-----------|
| 一 | 详设产物确认 | E 阶段文档完成后,M1 开工前 | 审阅 pi-protocol / m1-design / m1-tasks(各配一页速览) | 施工图可以按它开工吗? |
| 二 | 里程碑出口验收 | 每 M 收尾,主线程自验通过后 | Windows 真机实测 + 专项用例(如双向隔离)+ UI 走查 | 这个 M 算完成吗? |
| 三 | rework 超限熔断 | 同一任务卡失败循环 >3 轮 | 听取记录与判断:重拆卡 / 改详设 / 换做法 | 是执行问题还是设计问题? |

日常执行循环(派发→自验→验收→合入)不经用户,不消耗用户注意力。

## 9. 维护演进与知识沉淀

- **ADR**:开发期技术裁决记 `engineering/decisions.md`(编号 DR-N:背景/决定/影响);触发条件——协议变更、依赖类别新增、架构偏离既有裁决。S1 级裁决仍归 product-plan §2。
- **pi 上游升级**:锁版本(方案 B)→ 升级前跑 `regression-pi.sh` 四项冒烟 → 全绿才换 binary → 同步 `pi-protocol.md` + ADR 记录。
- **复盘**:每里程碑收尾写 `retro/mX.md`;教训必须回写本文档或 AGENTS.md(例:2026-09-10"未过 E 阶段直接想开工"即第一课,催生本文档)。
